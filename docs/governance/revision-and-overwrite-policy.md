# Revision and Overwrite Policy

Version: 0.2 Provisional
Status: Governance
Scope: Tessera model data, source-lineage, speculative design, and future implementation governance

---

## Status

This document defines the current provisional governance rule for modifying Tessera model data, card structures, taxonomy sections, Karma materials, symbol systems, reconciliation procedures, instruction manual language, and future digital schema planning.

No section of the system should be described as locked, final, permanent, or immune to review. All structures remain provisional unless later empirical validation and design review justify stronger language.

---

## Core Rule

Any proposed change that may overwrite, replace, remove, rename, reinterpret, or structurally affect an existing format must include an overwrite notice before the change is accepted.

This applies to changes in any part of the system, including:

- domain families;
- aspects;
- facets;
- expressions;
- reconciliation categories;
- question formats;
- response scales;
- symbol tags;
- Karma dimensions;
- Karma scenario structures;
- manual procedures;
- card-routing rules;
- scoring or interpretation charts;
- future database schema;
- AI-assisted interpretation logic;
- source-lineage documentation.

---

## Required Overwrite Notice

When a change may affect prior structure, the update should identify:

1. **Prior structure affected**: what existing model, file, deck, card type, or interpretive rule may be replaced.
2. **Reason for replacement**: why the proposed change improves construct clarity, reduces redundancy, improves analog usability, preserves empirical compatibility, prepares future infrastructure, or corrects an inaccuracy.
3. **Affected areas**: which taxonomy, Karma, symbol, reconciliation, manual, card-design, database, or AI-assistance sections may need review.
4. **Interpretive consequence**: whether the change affects scoring, routing, reconciliation, symbolic reference, moral interpretation, player-facing language, or future data structure.
5. **Confirmation requirement**: the potentially overwritten format should be confirmed before the change is encoded into repository materials.

---

## Empirical Preservation Rule

Empirically backed information should never be overwritten, deleted, or contradicted merely to simplify the Tessera model.

If an empirically supported construct is removed from the active architecture, the update must explain one of the following:

- the construct is represented elsewhere in the model;
- the construct is being preserved as source-lineage rather than active schema;
- the construct is outside the current scope;
- the construct is being separated from speculative Tessera mechanics;
- the construct requires further review before being operationalized.

The model may challenge, extend, or reinterpret established ideas only when the distinction between empirical evidence and Tessera speculation is made explicit.

---

## Speculative Modeling Rule

Speculative information is allowed and is important to Tessera's development. Speculative structures may include new taxonomy proposals, card mechanics, reconciliation pathways, symbolic reference systems, Karma patterns, ecological expansions, object-relations integrations, or future digital/AI-assisted infrastructure.

Speculative information must be labeled so it does not appear to be an established scientific finding.

Preferred labels:

- Provisional;
- Candidate;
- Hypothesis;
- Tessera-specific model;
- Design extrapolation;
- Entertainment-only mechanic;
- Requires validation;
- Source-informed but unvalidated.

---

## Entertainment vs. Assessment Boundary

Tessera may function as an analog entertainment tool, reflective identity map, educational model, and possible future testing framework.

These functions must not be confused.

If a section is designed only for entertainment, narrative play, or game balance, it should not be presented as empirical assessment.

If a section aims toward official testing, it must use cautious language and remain subject to validation requirements.

---

## Non-Absolute Language Requirement

Repository and manual language should avoid implying unsupported certainty. Use non-absolute phrasing where validation has not been completed.

Preferred language:

- suggests;
- may indicate;
- appears consistent with;
- may reflect;
- is compatible with;
- provides possible context for;
- should be reviewed against.

Avoid unsupported language:

- proves;
- guarantees;
- diagnoses;
- confirms definitively;
- always means;
- never means;
- locks;
- finalizes.

---

## Scientific Safeguards

The system should not claim psychometric validity, predictive certainty, diagnostic capability, moral certainty, or clinical utility unless supported by appropriate validation.

The following safeguards remain active unless explicitly revised:

- Do not infer moral character from personality scores alone.
- Do not treat symbols as independent psychometric scores.
- Do not treat participant self-description as automatically more accurate than response-pattern evidence.
- Do not collapse trait tendency, behavior, intent, and ethical consequence into one construct.
- Do not preserve a construct only because it comes from an established model if it creates redundancy in the active Tessera architecture.
- Do not remove empirically meaningful information without checking whether it is represented elsewhere.
- Do not encode speculative card mechanics as validated assessment logic.
- Do not let future digital implementation harden provisional structures into hidden absolutes.

---

## Analog and Future Digital Scope

Tessera is currently an analog card-based model focused on personality and morality psychology.

Future development may expand into broader theoretical systems such as ecology, object relations, identity dynamics, database-supported modeling, or AI-assisted interpretation. Those expansions should not retroactively rewrite the scientific status of the current personality/Karma model.

Any future digital implementation must preserve distinctions between:

```text
empirical source construct
Tessera speculative construct
card mechanic
symbol marker
interpretive hypothesis
validated score
entertainment-only element
```

## Repository Governance Rule

Before repo-wide governance claims are made, `docs/governance/repo-tree.md` and `docs/governance/model-file-manifest.md` should be reviewed.

If a file contains older conflicting language, either update it, classify it as superseded, or explain why it remains active.
